從連續故障到系統韌性：JDBC 連線與大流量衝擊

1. 系統崩潰的兩種形式 在維運高流量系統時，我們最害怕的往往不是寫出 Bug，而是面對那些「不可控」的因素。根據過去一年的經驗，我發現系統崩潰常來自兩個不可控因素： 內憂：資料庫連線莫名卡死，服務崩潰。 外患：高峰流量瞬間衝垮第三方服務，導致連鎖效應，最終拖垮自己。 這篇文章將還原一次我們處理會員系統資料庫連線的完整排查過程，以及我們如何建立多層防禦機制，避免第三方系統拖垮自己。 2. 內憂：不穩定的資料庫連線 某個週五晚上，我們的監控系統發出警報：會員系統的 Error Rate 飆升，大量的 API 請求噴出 GetConnectionTimeoutException。 詭異的是： 資料庫還活著：Cloud SQL 的 CPU 和 Memory 指標完全正常。 資料庫連線建不起來：監控顯示 Druid Connection Pool 的 active=0，但 creating=1，且 createElapseMillis 出現了已經累積數百萬毫秒。 這代表：應用程式試圖建立連線，但 TCP 層級既沒有成功，也沒有失敗，而是掉進了黑洞。 2.1 第一階段：懷疑 Stale Connection 我們最初的懷疑點是網路架構中的 Connection Pool Timeout 不一致。 我們的架構是 App -> HAProxy (Timeout 60s) -> Cloud SQL。而 Druid Connection Pool 的 minEvictableIdleTimeMillis 預設是 5 分鐘。 假設： HAProxy 已經砍掉了閒置連線，但 Druid 還以為這條連線是好的。當 Application 拿到這條「髒連線」時，就會發生異常。 我們進行了第一波優化： ...
