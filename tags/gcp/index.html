從 VM MySQL 5.7 到 Cloud SQL 8.0：一場「硬著陸」的整理與反思

為什麼搬？ 隨著公司推動雲原生，我們團隊雲原生化的路上，最棘手的挑戰，是 3 個還在 VM 裡的 MySQL 資料庫。 這 3 個資料庫是早期的外部廠商建立的，對目前的團隊來說，它們就像是三個「黑箱」。大家不熟悉，平常也盡量不去修改它。 除了版本較舊是 MySQL 5.7，也有著過度的 Over Provisioning，資料量只有幾十 GB，卻配置了 1 TB 的硬碟。 因此，這次的資料庫 Migration 的目標： 雲原生：搬遷至 Cloud SQL，減少維運成本。 版本升級：從 MySQL 5.7 升級至 8.0。 成本優化：解決資源浪費問題。 遷移策略 我有幸能主導這一項非常 Critical 的資料庫雲原生計畫，感恩主管給我這個機會。 現在回頭看，覺得我當時的選擇很「笨」。但當時，團隊對於各種雲端功能還沒那麼高的掌握。我並不知道 Cloud SQL 其實支援 External Replica，可以把 Cloud SQL 設為 VM 的 Slave。 在我當時的認知裡，資料庫遷移的標準作業程序： 停機 匯出 搬運 匯入 大功告成！ 嚴密的規劃 我們以較「笨」的方式執行，所以我更要確保每個執行步驟不能夠出錯。 我也做了 3 件事來確保 Migration 能順利執行： 視覺化流程 口頭討論流程容易有盲點，所以我用 PlantUML 畫出了時序圖，包含萬一出意外時的 Rollback Plan（當然是希望不要用到）。 什麼時間點切斷？什麼時間點執行 Dump？如果驗證失敗，切回舊 VM 的順序是什麼？這些都在圖上定義清楚，確保團隊認知一致。 ...
