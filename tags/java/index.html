從 PHP 到 Java：100+ API 的「考古」與重構之旅

Legacy 系統的負擔 這次想分享的挑戰，是要把外部廠商開發的 PHP Laravel 後端系統，接回內部營運。 這套系統有 100 多支 API，開發時間很早，隨著時間推移，逐漸成為團隊的負擔 缺乏文件：當初的商業邏輯不可考，程式碼是我們唯一能參考的文件。 維護困難：動態語言的特性加上開發時缺乏規範，出問題時也很難查詢。 效能瓶頸：資料庫查詢缺乏優化。 認知負擔：團隊主要使用 Java，維護這套系統是額外的認知負擔。 為了精簡 Tech Stack，和近一步掌握這套 Legacy 系統，我們決定開始 API Migration：將 PHP Laravel 系統從 Kubernetes 重寫為 Java Spring Boot，並部署至 Cloud Run。 遷移策略 100+ 支 API，不可能一次做好再上線。 我們採取的是 「絞殺榕模式」，漸進地取代舊系統。 我們的執行步驟大略如下： 挑選目標：從功能最獨立、風險最小的 API 開始。 並行：舊的 PHP 繼續跑，同時開發新的 Java 版本，舊 PHP 跑在原本的 K8s 上，新服務則部署到 Cloud Run。 API 落地：與 App 工程師配合，將新版 API 上線。 持續監控：觀察新 API 穩定後，才將舊 PHP 下線。 這種「一隻一隻搬」的策略，過程拉得較長，但每一次 API Migration 的風險都較為可控。 Code is the only Documentation 這次 Migration 最困難的是 「考古」。 因為沒有明確可靠的 Spec，我們必須讀懂原本 PHP 在做什麼，然後改寫成 Java。 ...
