從連續故障到系統韌性：JDBC 連線與大流量衝擊

December 10, 2025 · Julian Zhan

1. 系統崩潰的兩種形式#

在維運高流量系統時，我們最害怕的往往不是寫出 Bug，而是面對那些「不可控」的因素。根據過去一年的經驗，我發現系統崩潰常來自兩個不可控因素：

  1. 內憂：資料庫連線莫名卡死，服務崩潰。
  2. 外患：高峰流量瞬間衝垮第三方服務，導致連鎖效應，最終拖垮自己。

這篇文章將還原一次我們處理會員系統資料庫連線的完整排查過程，以及我們如何建立多層防禦機制，避免第三方系統拖垮自己。

2. 內憂：不穩定的資料庫連線#

某個週五晚上，我們的監控系統發出警報：會員系統的 Error Rate 飆升，大量的 API 請求噴出 GetConnectionTimeoutException。

詭異的是：

  • 資料庫還活著：Cloud SQL 的 CPU 和 Memory 指標完全正常。
  • 資料庫連線建不起來：監控顯示 Druid Connection Pool 的 active=0，但 creating=1，且 createElapseMillis 出現了已經累積數百萬毫秒。

這代表：應用程式試圖建立連線，但 TCP 層級既沒有成功，也沒有失敗，而是掉進了黑洞。

2.1 第一階段：懷疑 Stale Connection#

我們最初的懷疑點是網路架構中的 Connection Pool Timeout 不一致。 我們的架構是 App -> HAProxy (Timeout 60s) -> Cloud SQL。而 Druid Connection Pool 的 minEvictableIdleTimeMillis 預設是 5 分鐘。

假設： HAProxy 已經砍掉了閒置連線，但 Druid 還以為這條連線是好的。當 Application 拿到這條「髒連線」時，就會發生異常。

我們進行了第一波優化：

  1. 開啟 testOnBorrow：Application 拿資料庫連線前先 ping 一下。
  2. 縮短存活檢查：將 minEvictableIdleTimeMillis 降為 45s（小於 HAProxy 的 60s），搶先回收。

結果： 上線後，情況有所緩解，但沒有根治。

2.2 第二階段：抽絲剝繭，用 iptables 模擬黑洞#

如果連線是卡在 HAProxy 呢？為了驗證這個假設，我決定在測試環境 「模擬黑洞」。

我使用 iptables 在 HAProxy 層級直接 DROP 掉往 DB 的封包，模擬網路斷連但沒有收到 RST 封包的情境：

# 模擬封包丟失，製造網路黑洞
iptables -I OUTPUT -m string --algo bm --string "mysql" -j DROP

實驗結果：

  • 未設定 SocketTimeout： 應用程式的連線直接卡死，createElapseMillis 飆高。即使 iptables 恢復連線，應用程式也需等大約 1 分鐘才能正常連上資料庫。
  • 設定 SocketTimeout = 10s： 當 iptables 恢復後，服務在 1 秒內就自動恢復正常。

Root Cause： Druid & JDBC Driver 預設 socketTimeout 是 0。網路異常時，Druid 不會直接切斷連線重連。

但其實這次實驗沒有完美複現 Production 狀況。我們 Production 狀況是資料庫「永遠」連不上 (>3小時)，但這次實驗，資料庫還是會在最久 1 分鐘左右連上。 此時問題還沒被完全解決，只是再度被緩解一些。

2.3 第三階段：架構調整#

原先 HAProxy 便是我們要汰換掉的服務。藉由這個機會，我們也藉機把 HAProxy 給拔掉，讓 Application 直連 Cloud SQL，減少整個連線經過的節點數，降低資料庫連線不穩的干擾因素。

然而，移除掉 HAProxy 後，問題依然沒被完全解決。但到這時我們清楚知道，HAProxy 並不是元兇，唯一剩下的關鍵便是 Druid Connection Pool。

2.4 第四階段：HikariCP Burn-in Test#

HikariCP 是 Spring Boot 官方建議的套件，我們新開發的系統也都使用 HikariCP。但為了證實我們這次修改是真的能徹底解決資料庫連線問題（因為我們已經失敗太多次），我們決定要做更完整的驗證。

我們在 UAT 環境執行了嚴格的 Burn-in Test，試著把服務系統壓到極限，讓它出錯。

結果： 同樣的大流量下，Druid 會開始斷線，幾分鐘後才會再恢復。而 HikariCP 連線池都能在數秒內自動重建，吞吐量迅速回升，完全不需要人工介入。

雖然仍和我們觀察到「永不恢復」有所出入，但此實驗已經能夠證明，HikariCP 提供了比 Druid 更好的連線穩定性。

3. 最後一道防線：Liveness Probe#

即使有了 Timeout 和 HikariCP，我們還是不能保證應用程式永遠不會崩潰。

因此，我們進一步在 Cloud Run 加入 Liveness Probe (存活檢查)：

  • 機制：每 30 秒呼叫一次 API，該 API 會實際嘗試對 DB 執行 SELECT 1。
  • 策略：如果連續 3 次失敗，Cloud Run 會判定該容器不健康，並直接砍掉重啟 (Kill & Restart)。
  • 監控：我們設定了 Log-based Metric，當發生自癒重啟時，立即發送 Alert 通知團隊。

這確保了即便所有防禦都失效，系統也能自我修復，不會讓故障持續擴大。

4. 外患：被流量淹沒的外部服務#

解決了內憂，我們還得解決外患。我們有個容易有瞬時大流量的服務高度依賴第三方系統。在某次活動中，瞬間湧入的流量 (170 requests / 10s)，雖然不高，但已經遠超第三方系統極限 (60 requests / 10s)，導致第三方瘋狂 Timeout，進而拖垮我們。

4.1 多層次防禦體系：Rate Limiter, Bulkhead 與 Circuit Breaker#

為了避免這件事再重複發生，我們使用了 Resilience4j 的設計模式，建立了一套 「洋蔥式」的防禦體系：

  1. Rate Limiter (限流器)： 這是第一道關卡。我們計算了第三方系統能負荷的最大量，將單一 Instance 的請求上限設定為 2 QPS（4 台 Instances 共約 8 QPS）。這主要是為了防止過載。

  2. Bulkhead (艙壁隔離)： 光限制 QPS 不夠，如果外部服務回應變慢（Latency 變高），我們的 Thread 還是會被卡住。Bulkhead 限制了 「同時併發的執行數」。例如限制同時只能有 10 個執行緒在呼叫外部 API。一旦額滿，新的請求直接拒絕。

  3. Circuit Breaker (斷路器)： 這是最後的保險。當錯誤率超過閾值（例如 50%），斷路器會直接跳開 (Open)，阻斷所有請求一段時間。這能防止連鎖故障，並給予外部系統恢復的時間。

  • Before：流量衝進來 > 第三方系統崩潰 > Thread Pool 耗盡 > 全面崩潰。
  • After：
    • 流量過大 > Rate Limiter 擋掉。
    • 外部系統變慢 > Bulkhead 擋掉。
    • 外部系統掛掉 > Circuit Breaker 熔斷（快速失敗）。

結語#

系統韌性像是層層堆砌的概念：

  1. 連線層：優化 Eviction 策略，防止髒連線。
  2. 網路層：設定 socketTimeout，防止網路黑洞卡死。
  3. 元件層：引入 HikariCP 並通過 Burn-in Test，確保故障恢復能力。
  4. 自癒層：配置 Liveness Probe，讓系統具備「自癒」的能力。
  5. 流量層：實作 Rate Limiter、Bulkhead 與 Circuit Breaker，防止外部相依服務拖垮系統。

這次經驗教會我：永遠要去規劃失敗的狀況。 我們沒辦法完全避免，但能做的，就是做好準備，當災難發生時，讓系統盡可能優雅地處理，而不是全面崩潰。
