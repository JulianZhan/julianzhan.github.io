從 PHP 到 Java：100+ API 的「考古」與重構之旅

December 9, 2025

Legacy 系統的負擔#

這次想分享的挑戰，是要把外部廠商開發的 PHP Laravel 後端系統，接回內部營運。 這套系統有 100 多支 API，開發時間很早，隨著時間推移，逐漸成為團隊的負擔

  1. 缺乏文件：當初的商業邏輯不可考，程式碼是我們唯一能參考的文件。
  2. 維護困難：動態語言的特性加上開發時缺乏規範，出問題時也很難查詢。
  3. 效能瓶頸：資料庫查詢缺乏優化。
  4. 認知負擔：團隊主要使用 Java，維護這套系統是額外的認知負擔。

為了精簡 Tech Stack，和近一步掌握這套 Legacy 系統，我們決定開始 API Migration：將 PHP Laravel 系統從 Kubernetes 重寫為 Java Spring Boot，並部署至 Cloud Run。

遷移策略#

100+ 支 API，不可能一次做好再上線。

我們採取的是 「絞殺榕模式」，漸進地取代舊系統。

我們的執行步驟大略如下：

  1. 挑選目標：從功能最獨立、風險最小的 API 開始。
  2. 並行：舊的 PHP 繼續跑，同時開發新的 Java 版本，舊 PHP 跑在原本的 K8s 上，新服務則部署到 Cloud Run。
  3. API 落地：與 App 工程師配合，將新版 API 上線。
  4. 持續監控：觀察新 API 穩定後，才將舊 PHP 下線。

這種「一隻一隻搬」的策略，過程拉得較長，但每一次 API Migration 的風險都較為可控。

Code is the only Documentation#

這次 Migration 最困難的是 「考古」。 因為沒有明確可靠的 Spec，我們必須讀懂原本 PHP 在做什麼，然後改寫成 Java。

在這個過程中，我們學到了很多寶貴的經驗：

各種奇怪的邏輯，有些為了處理 Corner Case，有些就是亂寫#

在重構過程中，我常看到一些「看起來很奇怪」、「感覺很多餘」的邏輯。 我們對先前外包商的評價並不好，這是我們的刻板印象。因此一開始，我會直接把這些奇怪的邏輯 刪掉優化！

結果上線後，發現有些奇怪羅輯是為了處理一些 Corner case。

那些難以理解的 if-else，有些是為了處理某個兩年前的活動邏輯，或是為了相容某個舊版 App。

這些坑，持續的被踩到，然後再持續的被發現和優化。

能如何避免呢？這個我沒有一個完美答案，或許是需要有個能知道全局的人，才能理解當初的商業邏輯為何吧？否則，這種奇怪的邏輯，說他必要，有時候確實是要來處理某些 Corner case。

然而，有時又只是原本外包商亂寫而已。

順手償還的技術債#

API Migration 也是大幅優化系統的機會。 過程中，我們發現許多 SQL query 沒有 Index，導致 API 回應慢。

趁著這次重寫，我們做了兩件事：

  1. 設 Index：在資料庫補上缺少的 Index 來優化。
  2. Cache：在需要跟第三方系統互動取資料的 API，則大量使用 Cache。

具體成果#

經過了漫長的考古與重構，API Migration 的成果也很直接呈現：

  • API 回應速度提升 30%： 透過資料庫 Index 的補強、Cache 機制以及邏輯的重構，API Latency 顯著下降，直接提升了用戶的體驗。
  • 部署時間縮短 65%： 從原本 K8s，轉向 Cloud Run。大幅縮短了 CI/CD 時間。

反思：為什麼不繼續維護 Legacy？#

在專案進行中，我也曾反思：如果當初只是將 PHP 版本升級，或是遇到 Bug 就修復，是不是會比較快？

或許所花費的時間較短，但我們會錯失：

  1. 審視邏輯的機會：重寫強迫我們把每一行 Code 都看過一遍。
  2. 團隊一致性：現在團隊都使用 Java，溝通和未來開發成本大幅降低。

結語#

從 PHP 到 Java 的 Migration，也使我們有機會對舊系統優化。 短期來看，這樣的 API Migration 很消耗時間；長期來看，團隊的 Tech Stack 能夠統一！系統也能優化，未來的開發也能更順手！
