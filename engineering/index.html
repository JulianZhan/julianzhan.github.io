打造高併發下的交易一致性：從「27張優惠券」慘案談分散式系統設計

1. 前言：一個「自動化回滾」的慘痛教訓 在上一篇《系統韌性》中，我們談到了如何透過韌性機制讓系統在瞬間大流量中活下來。但活下來之後，我們面對的是更嚴苛的挑戰：資料正確性。 這是一個真實發生的慘案，源自於我們一次「想讓系統更好」的架構決策。 1.1 維運工具與自動化 在一個舊的兌換系統中，面對外部發券服務偶發的失敗，我們原本依賴一個「維運工具」，定期撈出失敗名單進行人工補發。 但團隊為了追求自動化，決定採用一個策略： 「如果呼叫外部發券 API Timeout，系統就當下直接執行 Rollback，讓用戶可以立刻重試。」 這個設計的出發點是善良的：我們不希望用戶因為網路或系統不穩定，導致資格被卡住。 而這個決策的風險是什麼？是如果外部發券 API 回覆太慢而 Timeout，用戶會多領到一張券。這個風險，我們認為相當可以接受。 1.2 弄巧成拙：27 張優惠券的誕生 然而，我們沒預期到的事，外部服務會一口氣 timeout 27次。 當時的流程是 「同步直接兌換」：用戶點擊 > 系統扣額度 > 呼叫外部 API 發券。 當外部 API 回應太慢至 Timeout 時： 系統判定失敗 > 釋放用戶額度。 外部系統其實已發券成功。 用戶發現還可以兌換，於是再次點擊。 這個流程在短時間內重複了數十次。最終有位客戶領到了 27 張折價券。 這是一個寶貴的經驗，我們低估了系統可能出錯的機率、時間長度和深度。我們以為用戶頂多多領到一張折價券，結果卻是27張。 2. 另一套系統的啟示：因「限制」而生的安全緩衝 慘案後，我剛好需要開發一套全新的兌換系統。 這個新系統有一個硬性限制：由於對接的外部服務特性，我們無法像舊系統那樣由後端直接呼叫 API 發券，必須改為產生一組「兌換連結」，讓用戶自己跳轉去網頁完成領取。 起初，我們對這個限制感到相當無奈。因為在直覺上，這代表用戶體驗（UX）被犧牲。 但就在實作過程中，我才後知後覺地發現：這個「被迫」的限制，竟然解決我們先前兌換時遇到的難題。 舊系統（直接兌換）： 系統試圖同步完成所有事，一旦 Timeout 就陷入「狀態未明」。 新系統（取連結模式）： 因為做不到直接兌換，強制切開了「鎖定資格」與「實際領取」。 這個不得不為之的「連結跳轉」，無意間創造了一個 「緩衝區」。如果外部系統 Timeout，用戶頂多是沒拿到連結（交易停在 Try 階段），而永遠不可能發生「系統以為失敗，但外部其實發券了」的狀況。 這個改變至關重要，它為我們創造了一個安全的 「緩衝區」，讓我們能安心地實作 TCC (Try-Confirm-Cancel)，在分散式交易下來確保交易的正確性。 3.
