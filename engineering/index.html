打造高併發下的交易一致性：從「27張優惠券」慘案談分散式系統設計

1. 前言：一個「自動化回滾」的慘痛教訓 在上一篇《系統韌性》中，我們談到了如何透過韌性機制讓系統在瞬間大流量中活下來。但活下來之後，我們面對的是更嚴苛的挑戰：資料正確性。 這是一個真實發生的慘案，源自於我們一次「想讓系統更好」的架構決策。 1.1 維運工具與自動化 在一個舊的兌換系統中，面對外部發券服務偶發的失敗，我們原本依賴一個「維運工具」，定期撈出失敗名單進行人工補發。 但團隊為了追求自動化，決定採用一個策略： 「如果呼叫外部發券 API Timeout，系統就當下直接執行 Rollback，讓用戶可以立刻重試。」 這個設計的出發點是善良的：我們不希望用戶因為網路不穩定，導致資格被卡住。 而這個決策的風險是什麼？是如果外部發券 API 回覆太慢而 Timeout，用戶會多領到一張券。這個風險，我們認為相當可以接受。 1.2 弄巧成拙：27 張優惠券的誕生 然而，我們沒預期到的事，外部服務會一口氣 timeout 27次。 當時的流程是 「同步直接兌換」：用戶點擊 > 系統扣額度 > 呼叫外部 API 發券。 當外部 API 回應太慢至 Timeout 時： 系統判定失敗 > 釋放用戶額度。 外部系統其實已發券成功。 用戶發現還可以兌換，於是再次點擊。 這個流程在短時間內重複了數十次。最終有位客戶領到了 27 張折價券。 這是一個寶貴的經驗，我們低估了系統可能出錯的機率、時間長度和深度。我們以為用戶頂多多領到一張折價券，結果卻是27張。 2. 架構進化：從「直接兌換」到「取得連結」 在建構新的兌換服務時，我們改變了交易流程。 我們不再「直接呼叫發貨」，而是改為 **「取得兌換連結」**模式。 這個改變至關重要，它為我們創造了一個安全的 「緩衝區」，讓我們能安心地實作 TCC (Try-Confirm-Cancel)，在分散式交易下來確保交易的正確性。 3. TCC 分散式交易模式 我們將一筆兌換交易拆解為三個明確的階段： Try (資源預留 & 取得連結)： 鎖定資源：在資料庫中鎖定全域庫存與該用戶的可用額度。狀態設為 RESERVED。 外部請求：取得結帳連結。 關鍵防護： 為什麼改成「取得連結」就能防禦？ 如果這一步 Timeout，我們可以放心地執行 Cancel。因為只要用戶「沒拿到連結」，他就無法進行後續的兌換。就算外部系統真的生成了一個的購物車連結，只要連結沒送達用戶手上，這筆交易就實質失敗了。 ...

從 VM MySQL 5.7 到 Cloud SQL 8.0：一場「硬著陸」的整理與反思
