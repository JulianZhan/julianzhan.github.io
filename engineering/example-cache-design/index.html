Cache Layer Design: Tradeoffs in a High-Traffic API

November 20, 2025

This is an example systems post. Replace with your own technical deep-dives.

Context#

When building a public API serving 100k+ requests per minute, caching becomes critical. But naive caching can create as many problems as it solves.

The Problem#

  • Database queries taking 200-500ms for frequently accessed data
  • Read-heavy workload (95% reads, 5% writes)
  • Data staleness acceptable up to 60 seconds
  • Need to handle cache invalidation without race conditions

Design Decisions#

1. Cache-aside pattern with TTL-based expiration#

Rather than write-through caching, we chose cache-aside:

  • Application checks cache first
  • On miss, queries database and populates cache
  • TTL set to 60 seconds

Why not write-through?

  • Write volume low enough that invalidation on write is acceptable
  • Simpler failure modes (stale cache vs. broken writes)
  • Easier to reason about in distributed system

2. Redis cluster vs single instance#

Chose Redis cluster despite added complexity:

  • Horizontal scalability for future growth
  • Better failure isolation
  • Worth the operational overhead for our scale

Results#

  • P95 latency reduced from 450ms to 25ms
  • Database load reduced by 87%
  • Cache hit rate: 94%

What I’d do differently#

  • Add cache warming on deployment to prevent thundering herd
  • Implement probabilistic early expiration to avoid stampede
  • Better monitoring on cache invalidation patterns
