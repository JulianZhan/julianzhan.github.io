打造高併發下的交易一致性：從「27張優惠券」慘案談分散式系統設計

December 10, 2025 · Julian Zhan

1. 前言：一個「自動化回滾」的慘痛教訓#

在上一篇《系統韌性》中，我們談到了如何透過韌性機制讓系統在瞬間大流量中活下來。但活下來之後，我們面對的是更嚴苛的挑戰：資料正確性。

這是一個真實發生的慘案，源自於我們一次「想讓系統更好」的架構決策。

1.1 維運工具與自動化#

在一個舊的兌換系統中，面對外部發券服務偶發的失敗，我們原本依賴一個「維運工具」，定期撈出失敗名單進行人工補發。 但團隊為了追求自動化，決定採用一個策略：

「如果呼叫外部發券 API Timeout，系統就當下直接執行 Rollback，讓用戶可以立刻重試。」

這個設計的出發點是善良的：我們不希望用戶因為網路或系統不穩定，導致資格被卡住。 而這個決策的風險是什麼？是如果外部發券 API 回覆太慢而 Timeout，用戶會多領到一張券。這個風險，我們認為相當可以接受。

1.2 弄巧成拙：27 張優惠券的誕生#

然而，我們沒預期到的事，外部服務會一口氣 timeout 27次。

當時的流程是 「同步直接兌換」：用戶點擊 > 系統扣額度 > 呼叫外部 API 發券。 當外部 API 回應太慢至 Timeout 時：

  1. 系統判定失敗 > 釋放用戶額度。
  2. 外部系統其實已發券成功。
  3. 用戶發現還可以兌換，於是再次點擊。

這個流程在短時間內重複了數十次。最終有位客戶領到了 27 張折價券。

這是一個寶貴的經驗，我們低估了系統可能出錯的機率、時間長度和深度。我們以為用戶頂多多領到一張折價券，結果卻是27張。

2. 另一套系統的啟示：因「限制」而生的安全緩衝#

慘案後，我剛好需要開發一套全新的兌換系統。

這個新系統有一個硬性限制：由於對接的外部服務特性，我們無法像舊系統那樣由後端直接呼叫 API 發券，必須改為產生一組「兌換連結」，讓用戶自己跳轉去網頁完成領取。

起初，我們對這個限制感到相當無奈。因為在直覺上，這代表用戶體驗（UX）被犧牲。

但就在實作過程中，我才後知後覺地發現：這個「被迫」的限制，竟然解決我們先前兌換時遇到的難題。

舊系統（直接兌換）： 系統試圖同步完成所有事，一旦 Timeout 就陷入「狀態未明」。

新系統（取連結模式）： 因為做不到直接兌換，強制切開了「鎖定資格」與「實際領取」。

這個不得不為之的「連結跳轉」，無意間創造了一個 「緩衝區」。如果外部系統 Timeout，用戶頂多是沒拿到連結（交易停在 Try 階段），而永遠不可能發生「系統以為失敗，但外部其實發券了」的狀況。 這個改變至關重要，它為我們創造了一個安全的 「緩衝區」，讓我們能安心地實作 TCC (Try-Confirm-Cancel)，在分散式交易下來確保交易的正確性。

3. TCC 分散式交易模式#

我們將一筆兌換交易拆解為三個明確的階段：

  • Try (資源預留 & 取得連結)：

    1. 鎖定資源：在資料庫中鎖定全域庫存與該用戶的可用額度。狀態設為 RESERVED。
    2. 外部請求：取得結帳連結。

    關鍵防護： 為什麼改成「取得連結」就能防禦？ 如果這一步 Timeout，我們可以放心地執行 Cancel。因為只要用戶「沒拿到連結」，他就無法進行後續的兌換。就算外部系統真的生成了一個的購物車連結，只要連結沒送達用戶手上，這筆交易就實質失敗了。

  • Confirm (確認提交)： 當用戶透過連結在外部完成結帳後，外部系統 Webhook 通知。此時我們才將狀態轉為 CONFIRMED，並正式扣除庫存。

  • Cancel (失敗補償)： 如果在 Try 階段取得連結失敗，系統自動觸發 Cancel，執行補償交易將額度釋放回池子裡。

4. Command Pattern 實戰#

架構確立了，但實作上我們需要一個機制來管理這些步驟的回滾。 一個兌換流程包含：預扣庫存 > 預扣個人額度 > 取得外部連結。

為了避免寫出難以維護的程式碼，我引入了 Command Pattern。

我們將每一個步驟封裝成獨立的 Command 物件，每個 Command 都必須實作兩個方法：

interface Command {
    void execute(); // 正向：扣庫存 / 扣額度
    void undo();    // 反向：補庫存 / 還額度
}

透過一個 CommandOrchestrator 來管理這些 Command 的 Stack。 當「取得連結」失敗時，Orchestrator 會自動從 Stack 中依序彈出已完成的 Command 並執行 undo()。 這不僅讓程式碼結構清晰，更確保了 「無論在哪一步失敗，庫存與額度都能乾淨地回到原點」。

5. 雙重鎖機制：並發控制的最後防線#

解決了流程控制，我們還得解決資料庫層級的 Race Condition，來防止超賣。 在新系統中，我們設計了兩層鎖定機制：

5.1 全域庫存：樂觀鎖 (Optimistic Lock)#

針對「限量 100 組」這種高併發搶購商品，我們採用 Version-based Optimistic Lock。

UPDATE inventory 
SET count = count - 1, version = version + 1
WHERE id = 1 AND version = current_version

誰先更新 version 誰就贏。這讓系統能在大流量下保持高效能，同時精準控制總庫存不超賣。

5.2 個人額度：悲觀鎖 (Pessimistic Lock)#

針對「每人限購 1 組」的限制，我們在檢查與預扣用戶額度時，使用了 Pessimistic Lock (SELECT ... FOR UPDATE)。

這強制資料庫對該用戶的紀錄進行序列化 (Serialization) 處理——同一時間，同一個用戶只能有一筆交易。

6. 韌性架構：洋蔥式防禦#

除了內部的鎖與交易模式，我們在外部也建立了一套 「洋蔥式」的防禦體系（詳見上一篇《系統韌性》）：

7. 壓測驗證#

  • 測試一：Flash Sale

    • 條件：500 個用戶同時搶購僅剩的 10 個商品
    • 結果：10 筆成功，490 筆失敗。

  • 測試二：Rapid Click

    • 條件：1 個用戶瞬間發送 30 次購買請求（個人限購 1 個）。
    • 結果：1 筆成功，29 筆失敗。

結語#

從「舊系統的直接兌換」到「新系統的連結緩衝」，我學到最重要的一課是：架構設計往往是在「限制」中尋找「最優解」。

那個原本讓我們覺得體驗不完美的「取得連結」限制，恰好實踐了分散式系統中最關鍵的 TCC 精神。

透過 Command Pattern 與鎖的機制，我們最終將這個「意外的發現」，轉化為一個能精準控制庫存與額度的系統。
